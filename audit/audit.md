# AI Bestie — Full Audit & Free-Tier-Safe Roadmap

## 1. Codebase Review — Findings

Every fix below respects the hard constraint: **100% free to run forever.**

### Direct answers to the three load-bearing questions

**What happens if both Gemini and OpenRouter fail or are rate-limited?**
Total failure *is* surfaced as an `error` SSE event (`server/src/services/chatService.ts:105`) — no infinite hang in the total-failure path. But getting there is bad: `openStream`/`consumeStream` use no `AbortController` and no timeout (`llmService.ts:75,157`), the fallback loop fires up to ~12 sequential HTTP calls, and there's **no SSE heartbeat** during the 20–40s backoff. Realistic outcomes: (a) the proxy/CDN/browser drops the idle SSE before the fallback chain finishes, leaving the orb stuck in `thinking` with no error event; (b) a hung upstream TCP connection blocks `reader.read()` forever with no deadline. **Partial/stalled failure = indefinite hang. This is the single biggest server-side reliability gap.**

**Does anything still reference the removed 5-layer prompt or semantic-memory system?**
- The **5-Layer System Prompt + Chain-of-Persona self-check are NOT removed** — still live in `server/src/models/Persona.ts:78-134`, invoked every chat request via `chatService → personaService.assembleSystemPrompt → persona.getSystemPrompt`. README line 14 and `docs/persona-system.md` are accurate. Don't touch them.
- The **only dead part of the 5-layer assembly is Layer 4**: `persona.getSystemPrompt(userContext?)` is always called with no argument (`personaService.ts:36-38`), so Layer 4 always renders "No prior user information available… first conversation" — even on later turns when session memory *is* being sent. Degrades prompt quality.
- **Semantic/episodic memory remnants**: `Conversation.ts` still carries dead fields `summary`, `metadata.emotionDetected`, `metadata.memoryExtracted` (never read/written). No `SemanticMemory`/`EpisodicMemory` model, no `$vectorSearch`. The dead remnants are schema fields + the `userContext` param + stale docs.

**Does anything quietly assume a paid MongoDB Atlas tier?**
No. Default is local Mongo (`config/index.ts:15`), no vector search anywhere, `Conversation.ts:86-96` sets a 48h TTL index that bounds storage — friendly to M0 512MB free. No connection-pool tuning that would exceed M0's ~100-connection cap. `.env.example` has placeholders only. **Free-tier-safe on the DB side.**

3. In `chatService.ts`: after the `token` loop, add a sentence-boundary accumulator; on a sentence, call `ttsService.synthesizeSentence()` and stream chunks as new SSE events `data: {type:'audio', content: base64, seq: n}`. Keep `token` events intact. Start synthesis after the `speaking` state event.
4. In `chatStore.ts`: add `case 'audio':` pushing base64 chunks into an `AudioContext` playback queue (ordered). Replaces accumulate-then-speak with true streaming audio.
5. In `speech.ts`: replace `speak()`/`stopSpeaking()` with an `AudioContext` queue manager fed by the `audio` case. **Keep `isSTTSupported`/`listenOnce` intact — STT unchanged.**
6. Graceful fallback: if Kokoro is unreachable (cold start/sleep), emit `type:'audio_unavailable'` → client falls back to a thin `speechSynthesis` wrapper.
7. Optional `TTS_PROVIDER` env: `edge` (best quality, fragile) vs `kokoro` (default, self-hosted).
